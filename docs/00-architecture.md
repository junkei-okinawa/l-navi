# システムアーキテクチャ設計書

## 1. 概要

LINE 公式アカウントを AI エージェントと一緒に構築する Web アプリケーション。

### 1.1 目的
- ユーザーが API キーを入力して LLM プロバイダーを選択可能
- AI との対話型ヒアリングで要件を深掘り
- LINE Messaging API を活用して公式アカウントの設定を自動化
- 構築中のアカウントイメージをチャットシミュレーターで動的プレビュー

### 1.2 設計原則

| 原則 | 説明 |
|---|---|
| **ユーザー主権** | 全てのデータをクライアント側で管理。ユーザーがデータ削除可能 |
| **クライアントファースト** | サーバー依存を最小化。Cloudflare Workers はプロキシのみ |
| **安全なデフォルト** | API キーは IndexedDB 平文。リスクを明告しユーザー教育で補完 |
| **並列実装可能** | モジュール間でブロッキングを起こさない設計 |

## 4. データフロー

### 4.1 API キー管理フロー

```
ユーザー
  │
  ├─(1) API キー入力画面でキーを入力
  │
  ├─(2) IndexedDB に保存 (平文)
  │     store: "api_keys"
  │     key: "default"
  │     value: { provider: "Gemini", apiKey: "..." }
  │
  └─(3) アプリ起動時に読み込み、LLM クライアントに注入
```

### 4.2 ヒアリングフロー

```
ユーザー
  │
  ├─(1) "カフェの公式アカウントを作りたい" と入力
  │
  ├─(2) AI が質問を生成
  │     "ターゲット層をお伺いできますか？"
  │
  ├─(3) ユーザー回答
  │
  ├─(4) AI が次の質問 OR 要件を確定
  │
  ├─(5) ヒストリーを indexed-db に保存
  │     stores: "hearing_sessions", "hearing_messages"
  │
  └─(6) 要件確定後、LINE API 設定を生成
```

### 4.3 LINE API 呼び出しフロー

```
Leptos アプリ
  │
  ├─(1) LINE API 呼び出しリクエスト
  │     POST /richmenu/create
  │     Body: { richmenudata: {...} }
  │
  ├─(2) Cloudflare Workers に転送
  │     Headers: X-Line-Channel-Access-Token: "..."
  │
  ├─(3) Workers が LINE API に転送
  │     POST https://api.line.me/v2/bot/richmenu
  │     Headers: Authorization: Bearer "..."
  │
  ├─(4) LINE API のレスポンスを返す
  │
  └─(5) Leptos アプリで結果処理
```

## 5. セキュリティ設計

### 5.1 API キー保護

| 対策 | 実装 |
|---|---|
| **HTTPS 強制** | 必須。開発中は localhost 許容 |
| **IndexedDB 利用** | localStorage より安全 (CORS 保護)。XSS 対策で補完 |
| **ユーザー教育** | 「平文保存のため共有端末では使用しない」「ブラウザデータ削除で消去可能」と明告 |
| **データ削除機能** | ユーザーが任意で API キー削除可能 |

### 5.2 LINE API キー保護

| 対策 | 実装 |
|---|---|
| **サーバーレスプロキシ** | Cloudflare Workers でキーを透過のみ |
| **キー保管なし** | Worker はキーを永続化しない |
| **CORS 制限** | 特定ドメインからのアクセスのみ許可 (オプション) |

## 6. エラーハンドリング

### 6.1 LLM API エラー

| エラー | 対応 |
|---|---|
| **401 Unauthorized** | API キー無効。再入力画面を表示 |
| **429 Too Many Requests** | リクエスト制限。待機時間を表示 |
| **5xx Server Error** | 一時的エラー。再試行を提案 |

### 6.2 LINE API エラー

| エラー | 対応 |
|---|---|
| **401 Unauthorized** | チャネルアクセストークン無効 |
| **400 Bad Request** | リクエストパラメータエラー。詳細を表示 |
| **404 Not Found** | リソース不存在 (例：リッチメニュー ID) |

## 7. 拡張性

### 7.1 将来の機能

| 機能 | 実装の容易さ |
|---|---|
| **複数プロバイダー併用** | 容易。データモデル拡張のみ |
| **エクスポート/インポート** | 容易。indexed-db データの JSON 出力 |
| **コラボレーション** | 困難。P2P またはサーバー必要 |

### 7.2 永続化の移行

将来的にサーバー永続化が必要になった場合:

```
indexed-db → SQLite (WASM) → PostgreSQL
         (ローカル)      (ローカル)    (サーバー)
```

移行コストは低く抑える (データアクセス層の抽象化)。

## 11. 並列実装のためのモジュール分割

| モジュール | 依存関係 | 並列可能 |

| **indexed-db 層** | なし | ✅ |

| **ヒアリングチャット** | LLM クライアント | ⚠️ 後続 |
| **LINE API クライアント** | なし | ✅ |
| **チャットシミュレーター** | LINE API クライアント | ⚠️ 後続 |
| **リッチメニューエディタ** | LINE API クライアント | ⚠️ 後続 |
| **Cloudflare Workers** | なし | ✅ |

**推奨並列グループ:**

```
グループ A (独立):
  - API キー管理
  - indexed-db 層
  - LINE API クライアント
  - Cloudflare Workers

グループ B (A 完了後):
  - LLM クライアント
  - チャットシミュレーター
  - リッチメニューエディタ

グループ C (B 完了後):
  - ヒアリングチャット
  - 統合テスト
```
